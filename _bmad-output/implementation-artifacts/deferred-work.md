- source_spec: `_bmad-output/implementation-artifacts/spec-1-7-credentials-in-credential-manager-write-only-panel.md`
  summary: Close the cross-process race in `KeyringSecrets`. `WinVaultKeyring.set_password` reads the shared `nextron-engine/<env>` target, moves its occupant to `<name>@nextron-engine/<env>`, then overwrites it. Two processes writing at once can therefore silently lose one credential. The in-process `threading.Lock` doesn't cover `nextron open`, which writes the one-time code from its own process.
  evidence: The adapter docstring in `nextron/adapters/secrets/__init__.py` documents it. Today the race needs Mac to save a credential at the same instant he runs `nextron open`, so it is rare. It becomes likely once any background job writes the keyring (Gmail OAuth token refresh, Epic 6). Preferred fix: give each secret its own target (service `nextron-engine/<env>/<name>`) so WinVault never shuffles entries, with a one-time move of existing entries. Fallback: a cross-process lock file in the data dir. Do it before the first background keyring writer (Story 6.1/6.2) at the latest; owner AD-12.
