## Intent

**Problem:** Draft revisions (4.12) are stored with no grounding at all, so a Draft that breaks the Step brief, a Playbook §4 banned pattern or the AD-18 contact-detail rule looks the same as a clean one.

**Approach:** Add the single pure definition `domain.grounding_rules.check(revision, brief, context)` (14 rule ids, a versioned rules list) and a `grounding_results` row per revision (owner `drafting`). Every revision `_append` writes (generated, operator edit, footer change) runs the rules in `_prepare`, before any write, and stores the result in the same unit: `fail` when any rule flags, else `pending` (the AI check, 4.14, decides `pass`).

## Boundaries & Constraints

**Always:**
- **`check(revision, brief, context) -> RulesResult(flags, rules_version)`**, pure, standard library and `nextron.domain` only. `revision`: subject, body (no signature/footer), `claims` (`None` or a tuple of `Claim(text, evidence_id | None, fact (fact_id, version) | None)`), `cited_signal_id`, `evidence_ids`, `fact_versions`. `brief`: the Step's `StepBrief` (`nextron.domain.sequences`). `context`: Step number, the allowed contact details (from Settings values), Evidence kinds by id, the Lead's Signals (id, type, class, tier, `score_only`, Evidence ids), the strongest live Event id (computed by the caller with `domain.signals.strongest_event`), the allowed `(fact_id, version)` set for the Draft's Segment and Market, and earlier Steps' current revisions (fact ids, cited Signal). A `Flag` is `(rule, span, explanation)`: `span` a substring of the subject or body (`""` only for a rule about the whole revision), `explanation` at most 200 characters, generated by code and never quoting Draft text. `RULES_VERSION` is a constant bumped whenever any rule or list changes. Flags come in a fixed order (rule-id order, then position).
- **The 14 rules** exactly as the story AC lists them (`word_limit`, `subject_rule`, `link_in_step1`, `unapproved_contact_detail`, `banned_phrase`, `attachment`, `price_or_audit_in_step`, `multiple_ctas`, `citation_outside_set`, `unhedged_absence`, `signal_count`, `wrong_signal`, `score_only_cited`, `repeated_angle`), ids equal to `nextron.domain.ai_test_sets.GROUNDING_RULE_IDS`. Word limits come from the brief via `sequences.max_words`; the subject limit from `brief.subject_rule`. Currency detection reuses `domain.prices.names_price`. Banned phrases and hedges are matched case-insensitively, ignoring punctuation, as whole phrases.
- **`claims is None`** → only the 8 text rules run (`word_limit` … `multiple_ctas`); the 6 claim rules need claims.
- **`grounding_results`** (new migration, owner `drafting`): ULID `id`; (`draft_id`, `rev`) unique with an FK to `draft_revisions(draft_id, rev)`; `status` ∈ {`pending`, `pass`, `fail`}; `flags` JSON array of `{rule, span, explanation}`; `rules_version`; `route_tuple_id` (nullable FK `ai_route_tuples`) and `served_model` (nullable), both NULL until 4.14; `checked_at`. One row per revision. Erasure: `flags` is personal data (spans quote Draft text): class `redact`, `ERASURE` entry `TOMBSTONED` (each span becomes `[erased]`, rule, explanation and status kept).
- **Wiring:** `_prepare` builds the context (brief from the Enrollment's Campaign's Sequence and the Draft's `step_no`; Segment and Market from the Campaign; Settings `sender_signature` and `privacy_notice_url`; the Lead's Evidence and Signals; `queries.playbook.allowed_facts`; earlier Step Drafts of the Enrollment) and runs `check`, before any write; `_append` gains `claims=None` and inserts the result row with the revision. `revise` and `recompose_ready` pass no claims. A context that can't be built (no brief) is a `LookupError` before any write, like 4.12's other checks.
- **Fixtures:** for every `tests/ai_sets/grounding/*.json` case, `check` over its input returns exactly the case's `expected.rules` (no flag on any `clean_control`). A fixture's `rules` may gain a rule only when that rule genuinely fires by this spec's definitions; each such edit is listed in Implementation Notes.

**Never:** the AI check, the grounding job, a `pass` status, the Lead page grounding badge or approval gating (4.14/Epic 5), storing claims on revisions (4.15), a second word counter / signal ranking / fact allow-list definition, a new dependency, a setting that disables a rule.

### Decisions made overnight (pending user review)
1. Storage: 4.13 creates `grounding_results` with 4.14's AC columns, since the rules' `fail` must be stored somewhere; 4.14 adds the AI part to it. Rules-only results are `fail` or `pending`, never `pass` (fail closed).
2. `wrong_signal` uses `domain.signals.strongest_event` (weight × decay; the spine's single definition) rather than the AC's "Tier first, then recency" summary.
3. Allowed contact details are the URLs, emails and phone numbers in `sender_signature` plus `privacy_notice_url`: no booking-link setting exists yet.
4. A Step 1 with no cited Signal flags `signal_count`, even for a later generic (fallback) Draft; 4.19 decides how generic Drafts treat it.
5. No UI in this story: the Lead page badge and flag list are 4.14's AC.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected | Error handling |
|---|---|---|---|
| Clean edit | ready Draft, edit within limits | rev N, `grounding_results` `pending`, `[]` flags | N/A |
| Rule break | edit with "circling back" and a stray URL | `fail`, flags `banned_phrase` + `unapproved_contact_detail` with spans | N/A |
| Settings link | body holds the `privacy_notice_url` | not `unapproved_contact_detail` (Step 1 still `link_in_step1`) | N/A |
| Step 1 limits | 80 words / 7-word subject / "RE: x" | `word_limit` / `subject_rule` / `subject_rule` | N/A |
| Step 2 limit | 70 words; 71 words | none; `word_limit` | N/A |
| No claims | edit (claims `None`) citing nothing | no claim rule runs | N/A |
| Generated with claims | claim cites Evidence outside the set | `citation_outside_set` | N/A |
| Footer change | text unchanged | new revision gets its own result row | N/A |
| Erasure | Contact erased | spans `[erased]`, rows kept | N/A |

## Implementation Notes

- `nextron/domain/grounding_rules.py` is the single definition: `RULE_IDS` (moved here; `ai_test_sets.GROUNDING_RULE_IDS` now aliases it), `TEXT_RULES`/`CLAIM_RULES`, `RULES_VERSION = 1`, `BANNED_PHRASES`, `ATTACHMENT_PHRASES`, `AUDIT_WORDS`, `HEDGES`, `GroundingStatus`, `Claim`, `RevisionInput`, `LeadSignal`, `EarlierStep`, `RulesContext`, `Flag`, `RulesResult` (`.status`: `fail` with any flag, else `pending`), `count_words` (the one word counter: whitespace runs holding a letter or digit) and `check`.
- **Fixture edits: none.** All 49 `tests/ai_sets/grounding/*.json` cases yield exactly their `expected.rules` unchanged.
- Interpretations made in code (the spec left them open): `subject_rule`'s "Re:/Fwd:" check (also `Fw:`) applies to Step 1 only (Playbook §4 "on a first email"); `link_in_step1` and `multiple_ctas` only on Step 1 (AC wording); `price_or_audit_in_step` follows the brief's `no_price`/`no_audit` flags (always true in the seed), a price flagged per sentence (span the sentence) via `names_price`, the audit as the whole word `audit`/`audits`; `unhedged_absence` looks for the hedge in the claim's own text, or in the sentence(s) holding every place that text appears (review pass 1); `signal_count` counts the cited Signal plus the Signals whose Evidence a claim cites when that Evidence isn't the cited Signal's; `wrong_signal` also flags a cited Signal when the Lead has no live Event; `score_only_cited` flags each claim citing a score-only Signal's Evidence, and a score-only cited Signal no claim covers; `repeated_angle` compares fact ids (any fact a follow-up's claims cite, not only a "main" one) and the cited Signal id with earlier Steps' current revisions (`fact_versions` and `cited_signal_id`). A claim whose text is in neither the subject nor body gets span `""`.
- Contact details: URLs (scheme, `www.` or bare `host.tld` with optional path; trailing punctuation dropped), emails, phones (7–15 digits; dates, year ranges and thousands-grouped numbers excluded). Equality by key: casefolded email; URL casefolded without scheme, leading `www.` or trailing `/`; phone digits only.
- `grounding_results` (migration `0046_4_13_grounding_results`, down `0045_4_12_draft_revisions`) adds `ck_grounding_results_fail` (status `fail` exactly when `flags` is non-empty) beyond the spec's columns; `served_model` is `String(64)`. No triggers (4.14 updates the row).
- Erasure tombstones every non-empty span to `[erased]` (an empty, whole-revision span stays `""`); `contact_export.COVERAGE` gains `grounding_results` → `Exported("drafting", "grounding_results")` and `queries.drafting.export_pii` returns that section.
- `_prepare(draft, subject, body, traceability, now, claims=None)` now also needs the traceability and time; the brief comes from the Campaign's Sequence (current version, not version-checked), Segment/Market from the Campaign.
- Review patches (pass 1):
  - `_url_key` drops `http://`/`https://` and a leading `www.` before casefolding and stripping a trailing `/`, so `www.x.com` in the signature approves `https://www.x.com` in a body.
  - Phone detection skips dotted, slashed or dashed dates (`19.11.2026`, `15-01-2024`, ISO), year ranges (`2019-2024`, `2019 - 2024`) and thousands-grouped numbers (`1.250.000`, `10 000 000`, `1,250,000`) via `_NOT_PHONE`; `020 7946 0318` and `+1 (614) 555-0142` still count.
  - `unhedged_absence` accepts a hedge in the claim text or in the `_sentences` around every place the claim text appears in the subject or body.
  - `wrong_signal`: with no cited Signal, the one Signal `signal_count` counts must be `strongest_event_id` (no double flag when the count isn't one).
  - `repeated_angle` also flags, once per Signal, a claim whose Evidence's owning Signals were cited by an earlier Step (not double-flagged with the cited-Signal flag).
  - A question is a sentence ending in `?` after trailing `!`, quotes and closing brackets are dropped (`?!` counts for `multiple_ctas`).
  - `_grounding` builds `evidence_kinds` from `research_queries.evidence_history` (superseded/retracted Absence Evidence is still hedge-checked) and raises `LookupError("the Draft's Sequence is unknown")` for an unresolved Sequence.
  - `grounding_results.tombstone` keeps empty spans `""`; migration 0046's docstring keeps `ck_grounding_results_rules_version` on one line.
  - New tests: unit cases for each rule change; app tests for a signature phone/URL approved in a Step 2 body, Step 1's cited Signal reaching Step 2 through `_earlier_steps`, retracted Absence Evidence, an unknown Sequence vs a Step without a brief, and empty spans surviving erasure. `RULES_VERSION` stays 1 (nothing stored yet).
